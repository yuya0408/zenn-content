## はじめに

実務でファインチューニング用の分散学習（FSDP2/DDP）基盤構築に携わった。分散学習の本格導入に向けた前段階の検証として、DGX Spark 2ノード構成を組んだ。その検証中に両ノードが完全フリーズし、復旧に物理アクセスを要した。その間、エラーもトレースバックも一切出力されていない。

直接の原因はGPUメモリの枯渇である。ただし、それが「メモリ不足」として観測可能な形で現れなかったこと、そして枯渇そのものの原因が最終的に **`model.train()` の呼び忘れ1行**に帰着したことが、この一件の本体だった。gradient checkpointingを有効化したつもりで、実際には一度も効いていなかった。一時、メモリ使用量の観点から「単ノードでは足りない」という判断をしかけたが、その判断は、checkpointingが効いていない状態で測ったpeakに基づくものだった。

この記事では、なぜOOMが検知できなかったのか、切り分けの過程でどの仮説を誤って掴んだのか、そして最終的に何が起きていたのかを記録した。

この記事を層別すると大きく2つに分けられる。

- **GB10（CPU/GPU共有メモリ）固有の話**：OSのoom-killerが機能しない構造（2節）
- **Hugging Face Transformers一般の話**：`gradient_checkpointing_enable()` は `model.train()` を呼ばない限り効かない。しかも `is_gradient_checkpointing` は `True` を返し続ける（4節）

3節は両者をつなぐ観測の話、5節は真の原因にたどり着くまでに外した仮説の記録である。2〜3節と4節は、それぞれ独立して読める。

もう1つ、分散学習を導入する前に知っておきたかったことがある。**分散化はメモリ問題を解決しなかっただけでなく、その問題を見えなくした**。単ノードならエラーとして出ていた失敗が、2ノードでは無言のハングになった（3節）。

### 環境

| 項目 | 内容 |
| --- | --- |
| ハードウェア | DGX Spark（GB10）× 2ノード（分散学習の導入前検証として構成） |
| ノード間接続 | ConnectX-7直結（2レール、MTU 9000） |
| GPU実効容量 | 1ノードあたり121.7GB（CPU/GPU共有のunified memory） |
| モデル | Qwen3.6-27B + PEFT/LoRA |
| 分散フレームワーク | PyTorch FSDP2（`fully_shard`）、NCCL over RDMA |

## 1. 結論

先に結論を書く。

- 2ノード分散学習がハングし、両ノードが応答を失った。原因はGPUメモリの枯渇だが、**エラーは一度も出ていない**
- 真の原因は `model.train()` の呼び忘れ。`AutoModelForCausalLM.from_pretrained()` はモデルをevalモードで返し、HFのgradient checkpointingはforward内部で `self.training` を見て分岐する。そのため `gradient_checkpointing_enable()` を呼んでいてもrecompute経路は一度も動いておらず、活性化が全層ぶん保持されていた
- この1行を足しただけで、`MAX_SEQ_LEN=2048` でのpeakメモリは **102.16GB → 41.41GB**。
- FSDP2の2ノード構成自体は最初から正しく動いていた（シャーディング・forward・backward・optimizer・チェックポイント保存/再開のいずれにも問題はなかった）

## 2. GB10ではGPUメモリ不足がoom-killerに見えない

### 主張

NVIDIAドライバが確保したメモリは、Linuxのoom-killerが参照するプロセス単位のRSSに計上されない。同じ理由でcgroup v2のメモリ会計からも外れるため、コンテナやジョブスケジューラ側でメモリ上限をかけても効かない。したがってCPU/GPU共有メモリ構成では、メモリ枯渇時にOSが正しい対処を取れない。

### 根拠

フリーズ後、物理復旧して `journalctl -b -1` を確認したところ、次のログが見つかった。

```text
NVRM: ... Out of memory [NV_ERR_NO_MEMORY] ... _memdescAllocInternal @ mem_desc.c:1359
```

このエラーは学習開始直後から始まっている。問題はその後の挙動である。

oom-killerはこの間に3回発動している。しかし毎回、`wireplumber` や `pipewire` といったメモリ消費と無関係な小さいデスクトッププロセスを終了させるだけだった。本当にメモリを保持しているプロセスには一度も到達していない。

oom-killerは自分の帳簿（プロセスRSS）を見て「最も食っているもの」を選ぶ。ドライバ側が握っているメモリはその帳簿に載らないため、判定は構造的に空振りし続ける。結果、システムは自己復旧の手段を失った。

### 一般化できる範囲

CPU/GPUがメモリを共有する構成では、**OS標準のOOM対処が働かない前提で設計する**必要がある。具体的には以下が必須になる。

- ジョブ側でのウォールクロックタイムアウト（プロセスが自力で死ねない以上、外から殺す）
- `nvidia-smi` による定期的な外形監視
- 物理アクセスなしで電源制御できる経路の確保

:::message
フリーズ状態でも Magic SysRq は反応した。通常のtty切り替えやキー入力が無反応でも、`Alt+SysRq+S`（sync）→ `U`（remount read-only）→ `O`（poweroff）の順で安全にシャットダウンできる。電源ボタン長押しの前に試す価値がある。ただし `kernel.sysrq` が有効になっている必要があるので、フリーズしてから調べることにならないよう、`sysctl kernel.sysrq` を平常時に確認しておくとよい。
:::

## 3. 分散実行ではOOMがエラーにならないことがある

### 主張

単一プロセスであれば `torch.OutOfMemoryError` として明示的に飛ぶ状況が、分散実行では原因不明のハングとして現れることがある。誰も待つのをやめないため、失敗が失敗として表面化しない。今回はまさにそれで、**同じ枯渇が単ノードではエラーとして出力されていた**（後述）。分散化はメモリ問題を解決しなかっただけでなく、その問題を見えなくした。

### 根拠

2ノードのログが途切れた時刻は1分差だった。当初はこれを「同一の集団通信（collective）中に両方が同時に落ちた」と読んだ。

だがこれは誤読だった。rank0のログは単語の途中で完全に途切れているのに対し、もう一方のランクはそのステップを通過して `Connected all rings` まで進んでおり、実際に枯渇したのは数時間後である。**ログ出力が止まった時刻と、プロセスが進めなくなった時刻は一致しない**（この読み違えは5節の仮説Aでも別の形で繰り返している）。

いずれにせよ、どちらのランクもエラーを報告していない。一方が動けなくなったとき、もう一方は「まだか」と待ち続けるだけである。

### なぜNCCLのwatchdogが止めてくれなかったか

PyTorchの `ProcessGroupNCCL` にはwatchdogスレッドがあり、既定では10分程度で応答のないcollectiveを検出してプロセスを異常終了させる。丸一日以上も無言でハングしたという話は、一見これと矛盾する。

理由は2節の状況にあると考えている。**watchdogも、GPUを掴んだプロセスと同じマシンの上で動いている**。ドライバ側のメモリが枯渇してシステム全体が応答を失った時点で、検出する側のスレッドもスケジュールされない。プロセス内の安全機構は、そのプロセスが動いていることを前提にしている。

外部からのウォールクロックタイムアウトと外形監視が必要になるのはこのためである。watchdogの設定は入れておく価値があるが、それだけでは今回のケースは救えない。

### 補足：エラーが出ても安心できない

単ノード（`WORLD_SIZE=1`）でのテスト中に、より厄介な挙動を観測した。

:::message alert
OOMエラーがログに出力された後もプロセスが終了せず、118GBを保持したまま25分間残り続けた。
:::

トレースバックが出ているからプロセスは死んだ、という前提は成り立たない。次のジョブを投入する前に `nvidia-smi` で実際の解放を確認する必要がある。

ただし裏を返せば、単ノードでは**エラーそのものは出ていた**。2ノードで丸一日以上完全に無言だったのとは対照的で、切り分けの難易度はここで大きく変わっている。

## 4. 真の原因：`model.train()` を呼んでいなかった

### 主張

`gradient_checkpointing_enable()` を呼んでいても、`model.train()` を呼ばなければgradient checkpointingは一切効かない。そしてそのことは、フラグやログを見ても分からない。

### 根拠

問題のコードはこうなっていた。

```python
model = AutoModelForCausalLM.from_pretrained(...)  # ← evalモードで返る
model.gradient_checkpointing_enable()
model.enable_input_require_grads()
# model.train()  ← これが無かった
```

`from_pretrained()` は推論を既定の用途としてモデルをevalモードで返す。一方、HF Transformersのgradient checkpointingは各層のforward内部で `self.training` を見て分岐する実装になっている。したがってevalモードのままでは、有効化を呼んでいてもrecompute経路には入らず、活性化は全層ぶん保持され続ける。

たちが悪いのは `model.is_gradient_checkpointing` が `training` を見ないことである。このプロパティは各サブモジュールに立てられた `gradient_checkpointing` フラグを集約するだけなので、evalモードのままでも `True` を返し続ける。**有効化のフラグが立っていることと、実際にrecomputeが走っていることは別問題**であり、このプロパティからは区別できない。当時のログにも「gradient checkpointing: enabled」相当の出力が出ており、そこで疑いを止めてしまった。

差分は1行、効果は以下の通り。

| 条件 | `MAX_SEQ_LEN` | peak memory（121.7GB中） |
| --- | ---: | ---: |
| `model.train()` なし | 2048 | 102.16GB |
| `model.train()` あり | 2048 | 41.41GB |
| `model.train()` あり | 12288 | 51.54GB |

2048トークンで102GBを消費していたのは、系列長が長すぎたからではなく、**活性化を1つも捨てていなかった**からである。checkpointingが効いた状態では、`MAX_SEQ_LEN` を12288まで伸ばしてもpeakの増加は約10GBに収まり、70GB以上の余裕が残る。「メモリ不足で使えない」と一度は結論した `MAX_SEQ_LEN=4096` 以降の全長は、実際には問題なく収まる。

### 確認方法

同じ踏み方をしないために、以下を確認手順として残しておく。

- `is_gradient_checkpointing` などのフラグではなく、**peak memoryの実測**で効いているかを判断する。
- LoRA/PEFT併用時は `enable_input_require_grads()` も必要になる。ベース重みが凍結されていると、checkpoint区間の入力にrequires_gradが立たず勾配が繋がらない。
- 学習ループに入る直前に `assert model.training` を1行入れておく

## 5. 外した仮説

真の原因だけでなく、検証の過程で外した仮説についても簡単に記載しておく。

### 仮説A：`init_process_group()` 内のNCCL初期化

rank0のログの最終行がこれで、しかも単語の途中で切れていた。

```text
Symmetric VA size=124GB
Symmetric memory is not supported. cuMemEnable 1, ...
```

`124GB` がGPU実効容量（121.7GB）とほぼ一致する。「NCCLがsymmetric memory機能のためにGPU全体に相当する仮想アドレス空間を予約しようとしており、unified memory構成ではそのVA予約が実メモリのコミットを引いている」という筋書きは、状況証拠として十分に強く見えた。

外れた理由は2つある。1つは、ログ自体が答えを持っていたこと。`Symmetric memory is not supported` と書いてある通りNCCLはフォールバックしており、124GBのVA予約はそもそも実行されていない。数字の一致（124GB ≒ 121.7GB）に引きずられて、同じ行の後半を読んでいなかった。

もう1つはより一般化できる。`dist.init_process_group()` はNCCLコミュニケータを**遅延生成**し、通信路の確立は最初のcollective呼び出し時に初めて起きる。ログに現れた初期化メッセージはモデルロード等がすべて終わった後に走った遅延初期化の出力であり、**ログ末尾は実行の先端を意味しない**。3節で停止時刻を1分差と読んだのも、同じ壊れ方の別の現れだった。

### 仮説B：系列長に対してメモリの余裕が足りない

`MAX_SEQ_LEN` を 12288 → 2048 に縮小した2ノードテストが `peak=102.16GB`（121.7GB中）で完走した。学習サンプル1件あたりのツールスキーマが大きく、本番の系列長は2048を大きく上回る。残り約20GBにその活性化が収まるとは思えなかった——これが2度目の誤った「最終結論」である。

外れた理由は4節の通りで、**2048で102GBという数字そのものが異常だった**。「短い系列でもすでに102GB使っている」を「だから長い系列は無理だ」と読んだが、正しくは「2048でこの数字はおかしい」と読むべきだった。

**入力を小さくして通ったことは、入力が原因だった証明にはならない。** メモリを浪費している別の要因があっても、入力を小さくすれば一時的には通ってしまう。「縮小したら通った」で切り分けを止めず、通った側の絶対値が妥当かを見る必要があった。

### その他に潰したもの

- **`flash-linear-attention` / `causal-conv1d` の欠落**：GatedDeltaNet層が純PyTorchのフォールバック実装で動作していた。実在の問題ではあったが、ハングの原因ではない
- **`fully_shard()` のラッピングが遅い**：64層で6〜7分かかり進行が止まったように見えたが、正常な挙動。リークでも異常でもない

## 6. 運用上の教訓

- **ウォールクロックタイムアウトは必須**。
- **プロセス内の安全機構はマシンが生きている前提で動く**。
- **フリーズ時はまず Magic SysRq を試す**。
- **エラーが出てもメモリは解放されていないことがある**。`nvidia-smi` で実確認する
- **分散学習のログ末尾は停止位置ではない**。遅延初期化とバッファリングを前提に読む
- **有効化フラグは「効いている」ことの証拠にならない**。`is_gradient_checkpointing` は `training` を見ないため、evalモードのままでも `True` を返す。
- **分散を入れる前に、単ノードで実測する**。「メモリが足りない」が思い込みだった場合、分散化は問題を解決しないばかりか、失敗をエラーから無言のハングに変えて切り分けを難しくする

---

## おわりに

切り分けに時間を要した障害の実体は、`model.train()` の1行だった。

時間がかかったのは、メモリ不足が**メモリ不足として観測できない**環境だったことに加えて、無効化されている機能が**有効に見えていた**ためである。どちらも「見えているものが実態と違う」という同じ形をしている。

CPU/GPU共有メモリ構成でのファインチューニングは日本語の情報がまだ少ない。同じ構造で詰まる人の時間短縮になれば幸いである。
