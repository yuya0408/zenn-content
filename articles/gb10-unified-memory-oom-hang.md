## はじめに

DGX Spark 2ノード構成でFSDP2による分散LoRAファインチューニングを実行したところ、両ノードが同時に完全フリーズし、復旧に物理アクセスを要した。48時間のあいだ、例外もトレースバックも一切出力されていない。

原因はGPUメモリ不足である。ただしそれが「メモリ不足」として観測可能な形で現れなかったことが問題の本体だった。この記事では、なぜOOMが検知できなかったのか、切り分けの過程でどの仮説を誤って掴んだのか、そして真因が学習データ側の設計にあったことを記録する。

この記事は2つの層を含む。

- **GB10（CPU/GPU共有メモリ）固有の話**：OSのoom-killerが機能しない構造
- **function calling学習一般の話**：ツールスキーマのトークン量が学習コストを支配する

読者の関心がどちらかに寄っている場合、2〜4節と5〜6節はそれぞれ独立して読める。

### 環境

| 項目 | 内容 |
| --- | --- |
| ハードウェア | DGX Spark（GB10）× 2ノード |
| ノード間接続 | ConnectX-7直結（2レール、MTU 9000） |
| GPU実効容量 | 121.7GB（CPU/GPU共有のunified memory） |
| モデル | 27Bクラス + PEFT/LoRA |
| 分散フレームワーク | PyTorch FSDP2（`fully_shard`）、NCCL over RDMA |

## 1. 結論

先に結論を書く。

- 2ノード分散学習が48時間ハングした。原因はGPUメモリ不足だが、**例外は一度も出ていない**
- 真因は学習サンプル1件あたりのツールスキーマが約11,400トークンあり、それが毎ステップ全量ロードされていたこと
- FSDP2の2ノード機構自体は正常に動作する。`MAX_SEQ_LEN` を 12288 → 2048 に縮小したところ、両ランクとも `loss=3.1649` / `peak=102.16GB`（121.7GB中）で最後まで完走した

つまり「分散学習の仕組みが壊れていた」のではなく、「載せようとしていた紙の量が物理的に多すぎた」だけである。にもかかわらず特定に3日を要した。その理由が2節と3節にあたる。

## 2. GB10ではGPUメモリ不足がoom-killerに見えない

### 主張

NVIDIAドライバが確保したメモリは、Linuxのoom-killerが参照するプロセス単位のRSSに計上されない。したがってCPU/GPU共有メモリ構成では、メモリ枯渇時にOSが正しい対処を取れない。

### 根拠

フリーズ後、物理復旧して `journalctl -b -1` を確認したところ、次のログが見つかった。

```text
NVRM: ... Out of memory [NV_ERR_NO_MEMORY] ... _memdescAllocInternal @ mem_desc.c:1359
```

このエラーは学習開始直後（14:13:47）から始まっている。問題はその後の挙動である。

oom-killerは当日中に3回発動している（18:58 / 20:07 / 翌16:16）。しかし毎回、`wireplumber` や `pipewire` といったメモリ消費と無関係な小さいデスクトッププロセスを終了させるだけだった。本当にメモリを保持しているプロセスには一度も到達していない。

oom-killerは自分の帳簿（プロセスRSS）を見て「最も食っているもの」を選ぶ。ドライバ側が握っているメモリはその帳簿に載らないため、判定は構造的に空振りし続ける。結果、システムは自己復旧の手段を失い、最終ログ（翌16:16）から電源投入まで完全に停止した。

### 一般化できる範囲

CPU/GPUがメモリを共有する構成では、**OS標準のOOM対処が働かない前提で設計する**必要がある。具体的には以下が必須になる。

- ジョブ側でのウォールクロックタイムアウト（プロセスが自力で死ねない以上、外から殺す）
- `nvidia-smi` による定期的な外形監視
- 物理アクセスなしで電源制御できる経路の確保

:::message
フリーズ状態でも Magic SysRq は反応した。通常のtty切り替えやキー入力が無反応でも、`Alt+SysRq+S`（sync）→ `U`（remount read-only）→ `O`（poweroff）の順で安全にシャットダウンできる。電源ボタン長押しの前に試す価値がある。
:::

## 3. 分散実行ではOOMが例外にならない

### 主張

単一プロセスであれば `torch.OutOfMemoryError` として明示的に飛ぶ状況が、NCCL/FSDP2のCレベルでの再試行に吸収され、原因不明のハングとして現れる。

### 根拠

2ノードの停止時刻は 14:13 と 14:14 で、1分差だった。同一の集団通信（collective）中に両方が落ちたことと整合する。

rank0のトレーニングログは単語の途中で完全に途切れて停止している。もう一方のランクはそのステップを通過して `Connected all rings` まで進んでいたが、数時間後に同じ枯渇状態に陥った。片方が動けなくなったとき、相方は「まだか」と待ち続けるだけで、誰もエラーを報告しない。

### 補足：例外が出ても安心できない

単ノード（`WORLD_SIZE=1`）でのテスト中に、より厄介な挙動を観測した。

:::message alert
OOM例外がログに出力された後もプロセスが終了せず、118GBを保持したまま25分間残り続けた。
:::

トレースバックが出ているからプロセスは死んだ、という前提は成り立たない。次のジョブを投入する前に `nvidia-smi` で実際の解放を確認する必要がある。

## 4. 切り分けで潰した仮説

ここが最も再利用価値のある部分だと考えている。正解だけを並べた記事は多いが、「もっともらしく見えて外れた仮説」は書かれにくい。3つとも、そう疑うだけの理由があった。

### 仮説A：`init_process_group()` 内のNCCL初期化

**なぜそう見えたか**

rank0のログの最終行がこれだった。

```text
Symmetric VA size=124GB
Symmetric memory is not supported. cuMemEnable 1, ...
```

しかも単語の途中で切れている。バッファがflushされる前にプロセスが停止したことを示唆する。

さらに `124GB` という数字がGPU実効容量（121.7GB）とほぼ一致していた。「NCCLがsymmetric memory機能のためにGPU全体に相当する仮想アドレス空間を予約しようとしており、unified memory構成ではそのVA予約が実メモリのコミットを引いているのではないか」という仮説は、状況証拠として十分に強く見えた。`cuMemEnable 1` はNCCLが `cuMem*` 系のVMMドライバAPIパスを使っていることを示しており、経路としても辻褄が合う。

**なぜ違ったか**

`dist.init_process_group()` はNCCLコミュニケータを**遅延生成**する。実際の通信路確立は最初のcollective呼び出し時に初めて発生する。

つまりログに現れたNCCL初期化メッセージは、モデルロード等がすべて終わった後に走った遅延初期化の出力であり、**ログ末尾は実行の先端を意味しない**。分散学習のログは、遅延初期化・複数プロセスの出力混在・バッファリングによって、「最後の行＝停止した場所」という単一プロセスの直感が壊れる。

### 仮説B：`flash-linear-attention` / `causal-conv1d` の欠落

**なぜそう見えたか**

これらが入っていないと、該当層が純PyTorchのフォールバック実装で動作する。実際に欠落しており、実在の問題ではあった。

**なぜ違ったか**

インストールする価値はあったが、ハングの直接原因ではなかった。ただし長系列でのメモリ消費への寄与は切り分けきれていないため、未検証項目として残している。

### 仮説C：`fully_shard()` のラッピングが遅い

**なぜそう見えたか**

64層のラッピングに6〜7分かかっており、進行が止まったように見えた。

**なぜ違ったか**

正常な挙動である。リークでも異常でもない。

## 5. 真因：学習データのトークン量

### 主張

学習サンプル1件あたりのツールスキーマが約11,400トークンあり、毎ステップ全量がGPUに載っていた。これが物理的な上限を超えていた。

### 根拠

`MAX_SEQ_LEN=2048` に縮小した2ノードテストでは、両ランクとも `loss=3.1649` / `peak=102.16GB`（121.7GB中）で正常に完走した。

重要なのは、**2048トークンという短い長さですでに102GBを消費している**という点である。残り約20GBで11,400トークンぶんを賄うことはできない。仕組みは正しく動いており、単にデータが大きすぎた。

## 6. 設計への反映

メモリ制約から出発した結果、学習データの構成そのものを見直すことになった。

**そもそも学習時に全ツールを載せる必要があるか。** 正解ツール + ディストラクタ数個をサンプリングして載せる方式であれば、系列長は劇的に短くなる。

興味深いのは、この変更がメモリ対策としてだけでなく**汎化の観点でも妥当である可能性**がある点だ。常に固定の全ツール集合を見せて学習した場合、モデルはその集合の存在を前提にしてしまう。実運用ではツール集合は変動するため、毎回異なる部分集合を見せるほうが、望ましい振る舞いに近い。

制約から出発した設計変更が、独立した理由でも正しい方向を向いていた、というのが今回いちばん収穫のあった点だった。

### 未検証の課題

- 実際に使用可能なシーケンス長の上限探索
- gradient checkpointing が FSDP2 + PEFT 併用で実際に効いているかの確認
- `flash-linear-attention` 導入による長系列でのメモリ消費への影響

## 7. 運用上の教訓

- **ウォールクロックタイムアウトは必須**。プロセスが自力で死ねない環境では、外から殺す仕組みがないと48時間が溶ける
- **フリーズ時はまず Magic SysRq を試す**。`S` → `U` → `O` で安全に停止できる
- **例外が出てもメモリは解放されていないことがある**。`nvidia-smi` で実確認する
- **分散学習のログ末尾は停止位置ではない**。遅延初期化を前提に読む

## おわりに

3日を要した障害の実体は「データが大きすぎた」という単純な事実だった。それでもこれだけの時間がかかったのは、メモリ不足が**メモリ不足として観測できない**環境だったためである。

CPU/GPU共有メモリ構成でのファインチューニングは日本語の情報がまだ少ない。同じ構造で詰まる人の時間短縮になれば幸いである。
