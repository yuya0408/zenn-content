## 1. 前提: どういうワークロードか

実務で、自社システムの AI チャット機能に使うローカル LLM の推論エンジンを選び直す必要があった。前提は次の通りである。

- **Mac Studio 上でのサービング**。クラウドに出せないデータを扱うため、オンプレのローカル推論が要件だった
- **マルチアクセス**。社内の複数ユーザーが同時に叩く
- **ツール呼び出し前提**。チャットから社内システムを操作するため、function calling が動かないと成立しない
- **ツールスキーマが膨大**。この結果、リクエストごとの入力トークンの大半が毎回ほぼ同一のスキーマ定義で占められる
- **マルチモデルロード**。用途ごとにモデルを使い分けるため、複数モデルを常駐させたい

この5つ目と4つ目が、エンジン選定のほぼすべてを決めた。

特に4つ目を補足しておく。ツールスキーマが膨大ということは、**毎リクエストの prefill で、ほぼ同じ長大なプレフィックスを再計算している**ということだ。会話本体が数十トークンでも、その前に数千トークンのスキーマが毎回付く。ここがキャッシュで効かせられるかどうかで、体感レイテンシ(TTFT)が大きく変わる。

## 2. 背景: なぜ Ollama から動くのか

それまでは Ollama を推論エンジンに採用していた。導入が容易で、動かすまでが速い。最初の一手としては妥当だったと考えている。

ただ、ここで正確を期しておきたい。**「Ollama はマルチモデルも同時アクセスも扱えない」というのは誤りである。** 実際には両方とも設定項目がある。

- `OLLAMA_MAX_LOADED_MODELS` ― 同時にロードするモデル数の上限(既定は GPU 数 × 3)
- `OLLAMA_NUM_PARALLEL` ― モデルあたりの並列リクエスト数

だから「できない」を移行理由にはできない。問題はもっと具体的なところにあった。

**ひとつ目は、並列数がコンテキストを分割することだ。** `OLLAMA_NUM_PARALLEL` を上げると、各スロットが自分の KV キャッシュ領域を持つ。実質的に「コンテキスト長 × 並列数」のメモリを確保する形になる。今回のように毎リクエストが数千トークンのツールスキーマを抱えていると、並列数を上げた瞬間にメモリが破裂する。並列性とコンテキスト長が真正面からトレードオフになってしまう。

**ふたつ目は、プレフィックスの再利用がリクエストをまたがないことだ。** Ollama にもプロンプトキャッシュはあるが、スロット単位の逐次的なものであって、「複数ユーザーの複数リクエストが、同一のツールスキーマ prefill を共有する」という使い方には向かない。今回のワークロードで一番効かせたいのは、まさにそこだった。

**みっつ目は、スケジューリングの粒度である。** Ollama はワーカースロットに FIFO でリクエストを流す。vLLM 系の continuous batching のように、生成途中のバッチへ新しいリクエストを差し込む仕組みではない。同時アクセス下での待ち時間の伸び方が変わってくる。

まとめると、移行の動機は「Ollama にできないから」ではなく、**「このワークロード(巨大な共通プレフィックス × 同時アクセス)に対して、Ollama のメモリモデルとスケジューラが構造的に不利だから」**である。逆に言えば、プレフィックスが短く同時アクセスも軽いなら、Ollama のままで何の問題もない。

:::message
ここで用語を整理しておく。後述の判断に効いてくる。

- **prefix caching** ― 同一の入力プレフィックスの KV を再計算せず使い回す。**TTFT(初回トークンまでの時間)を直接縮める**。今回の主目的はこちら
- **PagedAttention / paged KV cache** ― KV キャッシュをブロック単位で管理し断片化を防ぐ。**それ自体が1リクエストを速くするわけではない**。メモリ効率が上がった結果として同時実行数を増やせ、混雑時の待ち時間が改善する。また prefix 共有を実装可能にする土台でもある

「PagedAttention でレイテンシが改善する」と一括りにすると不正確になる。**単発の TTFT を縮めるのは prefix cache、混雑時のスループットと待ち行列を効かせるのが paged + continuous batching**、という分担で理解している。
:::

## 3. vllm-metal を検証し、見送った

まず当たったのが [vllm-metal](https://github.com/vllm-project/vllm-metal) である。`vllm-project` org 配下にあり、ドキュメントも docs.vllm.ai にホストされている。ただしリポジトリ自身の説明は "**Community maintained** hardware plugin for vLLM on Apple Silicon" であり、「vLLM 本体と同じ保証がある公式コンポーネント」と読むのは言い過ぎになる。org 配下の、コミュニティ保守のハードウェアプラグイン、という位置づけが正確だ。

MLX を計算バックエンドに据えて vLLM のエンジン・スケジューラ・OpenAI 互換サーバにそのまま接続する設計で、方向性としては理想的に見えた。

結論から言うと、今回の要件では見送った。理由は2つである。

**マルチモデルの同時ロードができなかった。** vllm-metal は vLLM 本体の作法をそのまま踏襲しており、1プロセス1モデルが基本になる。複数モデルを常駐させるならプロセスを並べて前段にルータを置くことになるが、それは要件に対して構成が重い。

**ツールコーリングパーサーが期待通りに機能しなかった。** そもそも README にも公開ドキュメントにも、tool calling / tool parser についての記載が見当たらない。動かなかったというより、**現時点でスコープに入っていない**と解釈するのが妥当だと考えている。ツール呼び出しが成立しない時点で、今回の用途では候補から外れた。

:::message alert
この2点は「vllm-metal が劣っている」という話ではない。単一モデルを Apple Silicon で高速に回すことに集中したプロジェクトであり、v0.2.0 では paged varlen kernel の導入で TTFT が大幅に改善したとアナウンスされている。**単一モデル・ツール呼び出しなしのユースケースなら、こちらの方が素直な選択になり得る。** 今回の要件と噛み合わなかった、というだけである。
:::

## 4. vllm-mlx を採用した

次に検証したのが [vllm-mlx](https://github.com/waybarrios/vllm-mlx) である。

**最初に断っておくと、これは非公式プロジェクトである。** vllm-project org 配下ではなく個人メンテナのリポジトリで、vLLM 本体から派生したものでもない。README も "inspired by vLLM" という表現をとっており、continuous batching と paged KV cache の設計思想を Apple Silicon / MLX に持ち込んだ独立実装、という位置づけになる。実務投入にあたってこの点をどう見積もったかは第7章に書く。

その上で、要件との噛み合い方が良かった。

**マルチモデルが本体機能として入っている。** `--models-config` に YAML を渡すと、複数モデルをレジストリとして常駐させられる。

```bash
vllm-mlx serve --models-config /etc/vllm-mlx/models.yaml --host 0.0.0.0 --port 8000
```

```yaml
manager:
  memory_budget_gb: 100
  idle_unload_seconds: 300
  contention_policy:
    strategy: wait_then_preempt
    wait_timeout_s: 45
    preempt_after_s: 15

models:
  - name: fast
    path: /path/to/model
    preload: true
    continuous_batching: true
    estimated_memory_gb: 4
```

振り分けは OpenAI 互換の `model` フィールドで行う。クライアントは `model: "fast"` と指定するだけでよく、登録がなければ利用可能な id を添えて 404 が返る。**前段にプロキシやルータを別コンポーネントとして立てる必要がない**のが、構成上いちばん効いた。マルチモデルを扱うと大抵このルータ層が増えて運用対象が増えるが、それを1プロセスに畳めた。

**ツールコーリングパーサーが揃っている。** `--tool-call-parser` で選択でき、`auto` / `mistral` / `qwen` / `llama` / `hermes` / `deepseek` / `kimi` / `granite` / `nemotron` / `xlam` / `functionary` / `glm47` が用意されている。主要どころは概ねカバーされている。

**paged KV cache と prefix cache が実装されている。** 今回の主目的だった、巨大なツールスキーマの prefill 再利用に手が届く。

## 5. Mac Studio でマルチモデルを載せるときの注意点

ここが本記事で一番伝えたい部分である。

### 5.1 vLLM の常識である `gpu_memory_utilization` は、ここには無い

vLLM 本体には `gpu_memory_utilization` があり、既定値は **0.9** である。これはクラスタ化した複数 GPU 環境を前提に、**1つの GPU の中で vLLM が単独で動く**ことを想定した最適化だ。GPU の 9 割をモデル重みと KV キャッシュのために先に確保してしまう。だから素の vLLM で複数モデルを同居させるときは、この値を下げて分け合う必要がある。

**ところが vllm-mlx はこの流儀を採っていない。** メモリ制御が二段構えになっている。

| 設定 | 対象 | 既定 |
|---|---|---|
| `manager.memory_budget_gb` / `--memory-budget-gb` | **モデル重みの常駐量のみ** | YAML 指定 |
| `--cache-memory-percent` | キャッシュに充てる RAM の割合 | **0.20** |
| `--cache-memory-mb` | キャッシュ上限の絶対値 | Auto |

罠は `memory_budget_gb` の定義にある。**これはモデル重みだけを数えており、KV キャッシュとアクティベーションを含まない。** 128GB 機で「100GB まで使ってよい」と設定すると、その 100GB は重みの話であって、KV キャッシュはその上に積まれる。ドキュメントが 128GB 機で 80〜100GB を目安としているのはこのためで、**残りを OS・アクティベーション・KV キャッシュで食う前提の数字**である。

`gpu_memory_utilization` の感覚で「9割まで使える」と思って重みを詰め込むと、同時アクセスが乗った瞬間に破綻する。ここは移行時に頭を切り替える必要がある。

### 5.2 効かせたい機能が、軒並みデフォルト無効

これが最大の落とし穴だった。vllm-mlx では、**移行の目的そのものだった機能が既定でオフになっている。**

| フラグ | 既定 |
|---|---|
| `--continuous-batching` | `False` |
| `--use-paged-cache` | `False` |
| `--prefix-trie-cache` | `False` |
| `--enable-auto-tool-choice` | `False` |

つまり、何も指定せずに起動すると **Ollama から移行した意味がほぼ無い状態で立ち上がる。** しかもエラーは出ない。普通に動いてしまうので、「移行したのに速くならない」という形でしか気づけない。関連パラメータも併せて見ておきたい。

- `--paged-cache-block-size` ― 1ブロックあたりのトークン数(既定 64)
- `--max-cache-blocks` ― 最大ブロック数(既定 1000)
- `--prefix-trie-cache-size` ― prompt trie のエントリ数上限(既定 **32**)
- `--prefix-trie-cache-memory-mb` ― trie のメモリ上限(既定なし)

特に `--prefix-trie-cache-size` の既定 32 は、常駐ユーザー数と会話本数によっては簡単に溢れる。ツールスキーマの prefill を効かせるのが目的なら、ここは実際の同時セッション数を見て決めるべき値だ。

### 5.3 ツールコーリングは、事前に軽量なテストを投げて確認する

パーサーが用意されているモデルでも、環境やモデルのバージョン、量子化の組み合わせによってパースを外すことがある。ツール呼び出しが前提のシステムでは、これは静かに壊れる類の障害になる。モデルは自然言語としてはもっともらしい応答を返し、ただ tool_calls が空になる、という形で失敗する。

そこで、**本番のスキーマを載せる前に、引数1つの最小ツールを1本だけ定義して呼ばせるスモークテストを用意した。** モデルを追加・更新するたびにこれを通す。数秒で終わるし、「パーサーが対応表に載っている」ことと「この環境で実際にパースできる」ことの間には差があるので、確認しておく価値がある。

## 7. 非公式プロジェクトを実務に入れる判断について

vllm-mlx は個人メンテナの非公式プロジェクトである。実務のシステムに据える以上、ここは素通りできない。

今回そう判断した理由と、置いた保険を書いておく。

- **OpenAI 互換 API で喋っている。** アプリ側は `/v1/*` を叩いているだけなので、エンジンを差し替えても呼び出し側の改修はほぼ生じない。これが一番大きい。撤退可能性が確保されている
- **撤退先が具体的にある。** 元の Ollama 構成は残してあり、切り戻しできる。将来 vllm-metal がマルチモデルとツール呼び出しに対応すればそちらも候補になる
- **バージョンを固定している。** 非公式プロジェクトは変更が速い。自動更新に任せない
- **ツール呼び出しのスモークテスト(5.3)を常設した。** 更新で静かに壊れる箇所を、更新のたびに機械的に踏む

逆に言えば、これらが確保できないなら採用しなかった。**「動いたから使う」ではなく「壊れたときに戻れるから使う」**という判断である。

## 8. まとめ

Mac Studio 上で、ツール呼び出し前提・マルチモデル・マルチアクセスのローカル LLM を動かすためにエンジンを選び直した記録である。現時点の結論をまとめる。

- **移行の理由は「Ollama にできないから」ではない。** Ollama もマルチモデルも並列も設定できる。不利だったのは、並列数がコンテキストを分割するメモリモデルと、リクエストをまたいだプレフィックス再利用が効かない点。**巨大な共通プレフィックス × 同時アクセス**という条件に構造的に噛み合わなかった
- **vllm-metal は見送った。** マルチモデル同時ロードと tool calling が、現時点でスコープに入っていない。単一モデル用途なら有力な選択肢であり続ける
- **vllm-mlx を採用した。** モデルレジストリで複数常駐と振り分けが1プロセスに畳め、別途ルータが要らない。主要モデルのツールパーサーが揃っている
- **`gpu_memory_utilization` の感覚を持ち込まない。** vllm-mlx は「重みの常駐予算」と「キャッシュ割合」の二段構えで、`memory_budget_gb` は重みしか数えない
- **効かせたい機能はデフォルトで無効。** `--continuous-batching` / `--use-paged-cache` / `--prefix-trie-cache` はいずれも既定 `False`。エラーが出ないまま「移行したのに速くならない」になる
- **ツール呼び出しは事前にスモークテストを通す。** 対応表に載っていることと、この環境で実際にパースできることは別である

そして最後に、この記事の一番大きな穴を明示しておく。**レイテンシの実測がまだ無い。** 上記はすべて「この構成なら効くはず」という設計上の見立てであって、数字で裏づけたものではない。第6章の計測設計に沿って測り、結果が出た時点で追記する。見立てが外れていた場合も、そのまま書く。
