## はじめに

DGX Spark 2ノード構成でFSDP2による分散LoRAファインチューニングを実行したところ、両ノードが同時に完全フリーズし、復旧に物理アクセスを要した。48時間のあいだ、例外もトレースバックも一切出力されていない。

直接の原因はGPUメモリの枯渇である。ただし、それが「メモリ不足」として観測可能な形で現れなかったこと、そして枯渇そのものの原因が最終的に **`model.train()` の呼び忘れ1行**に帰着したことが、この一件の本体だった。gradient checkpointingを有効化したつもりで、実際には一度も効いていなかった。

この記事では、なぜOOMが検知できなかったのか、切り分けの過程でどの仮説を誤って掴んだのか（真因にたどり着くまでに2度、誤った結論を「確定」として記録している）、そして最終的に何が起きていたのかを記録する。

この記事は2つの層を含む。

- **GB10（CPU/GPU共有メモリ）固有の話**：OSのoom-killerが機能しない構造（2節）
- **Hugging Face Transformers一般の話**：`gradient_checkpointing_enable()` は `model.train()` を呼ばない限り効かない。しかも `is_gradient_checkpointing` は `True` を返し続ける（5節）

3〜4節は、この2つをつなぐ切り分けの過程にあたる（分散学習のログをどう読み違えたか、どの仮説を外したか）。関心がどちらかに寄っている場合、2〜4節と5節はそれぞれ独立して読める。

| ノード間接続 | ConnectX-7直結（2レール、MTU 9000） |

## 1. 結論

先に結論を書く。

- 2ノード分散学習が48時間ハングした。原因はGPUメモリの枯渇だが、**例外は一度も出ていない**
- 真因は `model.train()` の呼び忘れ。`AutoModelForCausalLM.from_pretrained()` はモデルをevalモードで返し、HFのgradient checkpointingはforward内部で `self.training` を見て分岐する。そのため `gradient_checkpointing_enable()` を呼んでいてもrecompute経路は一度も動いておらず、活性化が全層ぶん保持されていた
- この1行を足しただけで、`MAX_SEQ_LEN=2048` でのpeakは **102.16GB → 41.41GB**。本番の最長系列（約11,400トークン）でも peak 51.54GB / 121.7GB で、70GB以上の余裕がある
- FSDP2の2ノード構成自体は最初から正しく動いていた（シャーディング・forward・backward・optimizer・チェックポイント保存/再開のいずれにも問題はなかった）

つまり「分散学習の仕組みが壊れていた」わけでも、「載せようとしていた紙の量が物理的に多すぎた」わけでもなく、**読み終えた紙を捨てる機能を有効にし忘れていた**だけである。にもかかわらず特定に3日を要し、その途中で2度、誤った結論を「確定」として書いている。その理由が2〜4節にあたる。

## 2. GB10ではGPUメモリ不足がoom-killerに見えない

### 主張

NVIDIAドライバが確保したメモリは、Linuxのoom-killerが参照するプロセス単位のRSSに計上されない。同じ理由でcgroup v2のメモリ会計からも外れるため、コンテナやジョブスケジューラ側でメモリ上限をかけても効かない。したがってCPU/GPU共有メモリ構成では、メモリ枯渇時にOSが正しい対処を取れない。

### 根拠

フリーズ後、物理復旧して `journalctl -b -1` を確認したところ、次のログが見つかった。

```text
NVRM: ... Out of memory [NV_ERR_NO_MEMORY] ... _memdescAllocInternal @ mem_desc.c:1359
```

このエラーは学習開始直後（14:13:47）から始まっている。問題はその後の挙動である。

oom-killerは当日中に3回発動している（18:58 / 20:07 / 翌16:16）。しかし毎回、`wireplumber` や `pipewire` といったメモリ消費と無関係な小さいデスクトッププロセスを終了させるだけだった。本当にメモリを保持しているプロセスには一度も到達していない。

oom-killerは自分の帳簿（プロセスRSS）を見て「最も食っているもの」を選ぶ。ドライバ側が握っているメモリはその帳簿に載らないため、判定は構造的に空振りし続ける。結果、システムは自己復旧の手段を失った。

時系列を整理しておく。最初のNVRM OOM（14:13:47）から最終ログ（翌16:16）までが約26時間、そこからさらに電源を入れ直すまで、ログを1行も残さないまま停止し続けた。冒頭で「48時間」と書いたのはこの通算時間である。

### 一般化できる範囲

CPU/GPUがメモリを共有する構成では、**OS標準のOOM対処が働かない前提で設計する**必要がある。具体的には以下が必須になる。

- ジョブ側でのウォールクロックタイムアウト（プロセスが自力で死ねない以上、外から殺す）
- `nvidia-smi` による定期的な外形監視
- 物理アクセスなしで電源制御できる経路の確保

:::message
フリーズ状態でも Magic SysRq は反応した。通常のtty切り替えやキー入力が無反応でも、`Alt+SysRq+S`（sync）→ `U`（remount read-only）→ `O`（poweroff）の順で安全にシャットダウンできる。電源ボタン長押しの前に試す価値がある。ただし `kernel.sysrq` が有効になっている必要があるので、フリーズしてから調べることにならないよう、`sysctl kernel.sysrq` を平常時に確認しておくとよい。
:::

## 3. 分散実行ではOOMが例外にならないことがある

### 主張

単一プロセスであれば `torch.OutOfMemoryError` として明示的に飛ぶ状況が、分散実行では原因不明のハングとして現れることがある。誰も待つのをやめないため、失敗が失敗として表面化しない。

### 根拠

2ノードのログが途切れた時刻は 14:13 と 14:14 で、1分差だった。当初はこれを「同一の集団通信（collective）中に両方が同時に落ちた」と読んだ。

だがこれは誤読だった。rank0のログは単語の途中で完全に途切れているのに対し、もう一方のランクはそのステップを通過して `Connected all rings` まで進んでおり、実際に枯渇したのは数時間後である。**ログ出力が止まった時刻と、プロセスが進めなくなった時刻は一致しない**（この読み違えは4節の仮説Aでも別の形で繰り返している）。

いずれにせよ、どちらのランクもエラーを報告していない。片方が動けなくなったとき、相方は「まだか」と待ち続けるだけである。

### なぜNCCLのwatchdogが止めてくれなかったか

PyTorchの `ProcessGroupNCCL` にはwatchdogスレッドがあり、既定では10分程度で応答のないcollectiveを検出してプロセスを異常終了させる。48時間無言でハングしたという話は、一見これと矛盾する。

理由は2節の状況にあると考えている。**watchdogも、GPUを掴んだプロセスと同じマシンの上で動いている**。ドライバ側のメモリが枯渇してシステム全体が応答を失った時点で、検出する側のスレッドもスケジュールされない。プロセス内の安全機構は、そのプロセスが動いていることを前提にしている。

外部からのウォールクロックタイムアウトと外形監視が必要になるのはこのためである。watchdogの設定は入れておく価値があるが、それだけでは今回のケースは救えない。

### 補足：例外が出ても安心できない

単ノード（`WORLD_SIZE=1`）でのテスト中に、より厄介な挙動を観測した。

:::message alert
OOM例外がログに出力された後もプロセスが終了せず、118GBを保持したまま25分間残り続けた。
:::

トレースバックが出ているからプロセスは死んだ、という前提は成り立たない。次のジョブを投入する前に `nvidia-smi` で実際の解放を確認する必要がある。

## 4. 切り分けで潰した仮説

ここが最も再利用価値のある部分だと考えている。正解だけを並べた記事は多いが、「もっともらしく見えて外れた仮説」は書かれにくい。4つとも、そう疑うだけの理由があった。とくに仮説Dは、いったん「これが真因である」と結論して記録まで残している。

### 仮説A：`init_process_group()` 内のNCCL初期化

**なぜそう見えたか**

rank0のログの最終行がこれだった。

```text
Symmetric VA size=124GB
Symmetric memory is not supported. cuMemEnable 1, ...
```

しかも単語の途中で切れている。バッファがflushされる前にプロセスが停止したことを示唆する。

さらに `124GB` という数字がGPU実効容量（121.7GB）とほぼ一致していた。「NCCLがsymmetric memory機能のためにGPU全体に相当する仮想アドレス空間を予約しようとしており、unified memory構成ではそのVA予約が実メモリのコミットを引いているのではないか」という仮説は、状況証拠として十分に強く見えた。`cuMemEnable 1` はNCCLが `cuMem*` 系のVMMドライバAPIパスを使っていることを示しており、経路としても辻褄が合う。

**なぜ違ったか**

まず、ログ自体が答えを持っていた。`Symmetric memory is not supported` と書いてある通り、NCCLはsymmetric memoryを有効化できずフォールバックしている。124GBのVA予約は、そもそも実行されていない。都合のいい数字の一致（124GB ≒ 121.7GB）に引きずられて、同じ行の後半を読んでいなかった。

そのうえで、より一般化できる誤りがある。`dist.init_process_group()` はNCCLコミュニケータを**遅延生成**する。実際の通信路確立は最初のcollective呼び出し時に初めて発生する。

つまりログに現れたNCCL初期化メッセージは、モデルロード等がすべて終わった後に走った遅延初期化の出力であり、**ログ末尾は実行の先端を意味しない**。分散学習のログは、遅延初期化・複数プロセスの出力混在・バッファリングによって、「最後の行＝停止した場所」という単一プロセスの直感が壊れる。3節で停止時刻を1分差と読んだのも、同じ壊れ方の別の現れだった。

### 仮説B：`flash-linear-attention` / `causal-conv1d` の欠落

**なぜそう見えたか**

これらが入っていないと、該当層が純PyTorchのフォールバック実装で動作する。実際に欠落しており、実在の問題ではあった。

**なぜ違ったか**

インストールする価値はあったが、ハングの直接原因ではなかった。ただし長系列でのメモリ消費への寄与は切り分けきれていないため、未検証項目として残している。

### 仮説C：`fully_shard()` のラッピングが遅い

**なぜそう見えたか**

64層のラッピングに6〜7分かかっており、進行が止まったように見えた。

**なぜ違ったか**

正常な挙動である。リークでも異常でもない。

### 仮説D：系列長に対してGPUメモリの余裕が足りない

**なぜそう見えたか**

`MAX_SEQ_LEN` を 12288 → 2048 に縮小した2ノードテストが、両ランクとも `loss=3.1649` / `peak=102.16GB`（121.7GB中）で完走した。縮小したら通った、という事実は強い。しかも学習サンプル1件あたりのツールスキーマは約11,400トークンあり、本番の系列長は2048の5.6倍になる。残り約20GBの枠にその活性化が収まるとは思えなかった。

この時点で「真因は学習データのトークン量である」と結論し、記録にも残している。仮説Aの訂正に続く、2度目の誤った「最終結論」だった。

**なぜ違ったか**

**2048で102GBという数字そのものが異常だった**、というのが答えである。gradient checkpointingが効いていれば同条件で41.41GBに収まる（5節）。「短い系列でもすでに102GB使っている」を「だから長い系列は無理だ」と読んだが、正しくは「2048でこの数字はおかしい」と読むべきだった。

一般化するとこうなる。**入力を小さくして通ったことは、入力が原因だった証明にはならない。** メモリを浪費している別の要因があっても、入力を小さくすれば一時的には通ってしまう。切り分けとして「縮小したら通った」で止めず、通った側の絶対値が妥当かを見る必要があった。

なお、1サンプル約11,400トークンという事実自体は正しい。それが物理的な上限を超えていたという判断だけが誤りだった（6節）。

## 5. 真因：`model.train()` を呼んでいなかった

### 主張

`gradient_checkpointing_enable()` を呼んでいても、`model.train()` を呼ばなければgradient checkpointingは一切効かない。そしてそのことは、フラグやログを見ても分からない。

### 根拠

問題のコードはこうなっていた。

```python
model = AutoModelForCausalLM.from_pretrained(...)  # ← evalモードで返る
model.gradient_checkpointing_enable()
model.enable_input_require_grads()
# model.train()  ← これが無かった
```

`from_pretrained()` は推論を既定の用途としてモデルをevalモードで返す。一方、HF Transformersのgradient checkpointingは各層のforward内部で `self.training` を見て分岐する実装になっている。したがってevalモードのままでは、有効化を呼んでいてもrecompute経路には入らず、活性化は全層ぶん保持され続ける。

たちが悪いのは `model.is_gradient_checkpointing` が無条件に `True` を返す点である。**有効化のフラグが立っていることと、実際にrecomputeが走っていることは別問題**であり、このプロパティからは区別できない。当時のログにも「gradient checkpointing: enabled」相当の出力が出ており、そこで疑いを止めてしまった。

差分は1行、効果は以下の通り。

| 条件 | `MAX_SEQ_LEN` | peak memory（121.7GB中） |
| --- | ---: | ---: |
| `model.train()` なし | 2048 | 102.16GB |
| `model.train()` あり | 2048 | 41.41GB |
| `model.train()` あり | 約11,400（本番最長） | 51.54GB |

2048トークンで102GBを消費していたのは、系列長が長すぎたからではなく、**活性化を1つも捨てていなかった**からである。checkpointingが効いた状態では、系列長を5.6倍にしてもpeakの増加は約10GBに収まり、70GB以上の余裕が残る。4節の仮説Dが「メモリ不足で使えない」と結論した `MAX_SEQ_LEN=4096` 以降の全長は、実際には問題なく収まる。

### 確認方法

同じ踏み方をしないために、以下を確認手順として残しておく。

- `is_gradient_checkpointing` などのフラグではなく、**peak memoryの実測**で効いているかを判断する。`model.train()` の有無で2回測れば、桁で差が出るので迷わない
- LoRA/PEFT併用時は `enable_input_require_grads()` も必要になる。ベース重みが凍結されていると、checkpoint区間の入力にrequires_gradが立たず勾配が繋がらない。ただしこれは `model.train()` の代わりにはならない（今回は両方書いたうえで `train()` だけが抜けていた）
- 学習ループに入る直前に `assert model.training` を1行入れておく

## 6. データ設計はどうなったか

5節の修正により、当初「メモリ制約から必須」と考えていた学習データ側の変更は、**メモリを理由としては不要になった**。本番の最長系列（約11,400トークン）はそのまま通る。

ただし検討自体は残った。1サンプル約11,400トークンの大半をツールスキーマが占め、それが毎ステップ全量ロードされている構成であることは変わらないからである。**そもそも学習時に全ツールを載せる必要があるか。** 正解ツール + ディストラクタ数個をサンプリングして載せる方式であれば系列長は劇的に短くなり、同じ時間でより多くのステップを回せる。

さらにこの変更は、**汎化の観点でも妥当である可能性**がある。常に固定の全ツール集合を見せて学習した場合、モデルはその集合の存在を前提にしてしまう。実運用ではツール集合は変動するため、毎回異なる部分集合を見せるほうが、望ましい振る舞いに近い。

メモリ上の必然性が消えた結果、この変更は「やらざるを得ないこと」から「速度と汎化のためにやる価値があること」へ位置づけが変わった。判断材料としてはむしろ健全になっている。

## 7. 運用上の教訓

- **ウォールクロックタイムアウトは必須**。プロセスが自力で死ねない環境では、外から殺す仕組みがないと48時間が溶ける
- **プロセス内の安全機構はマシンが生きている前提で動く**。`ProcessGroupNCCL` のwatchdogは設定する価値があるが、システムごと固まれば検出側も止まる。監視は外に置く
- **フリーズ時はまず Magic SysRq を試す**。`S` → `U` → `O` で安全に停止できる（`kernel.sysrq` の有効化は平常時に確認しておく）
- **例外が出てもメモリは解放されていないことがある**。`nvidia-smi` で実確認する
- **分散学習のログ末尾は停止位置ではない**。遅延初期化とバッファリングを前提に読む
- **有効化フラグは「効いている」ことの証拠にならない**。`is_gradient_checkpointing` は無条件に `True` を返す。効果は peak memory の実測で確認する
- **入力を小さくして通ったことは、入力が原因だった証明ではない**。通った側の絶対値が妥当かまで見る

## おわりに

切り分けに3日を要した障害の実体は、`model.train()` の1行だった。しかもその過程で2度、別の結論を「最終結論」として記録している（NCCL初期化 → データのトークン量 → gradient checkpointingの無効化）。

これだけの時間がかかったのは、メモリ不足が**メモリ不足として観測できない**環境だったことに加えて、無効化されている機能が**有効に見えていた**ためである。どちらも「見えているものが実態と違う」という同じ形をしている。

CPU/GPU共有メモリ構成でのファインチューニングは日本語の情報がまだ少ない。同じ構造で詰まる人の時間短縮になれば幸いである。
